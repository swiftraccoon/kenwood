# Transport + APRS + APRS-IS review

Scope: `thd75/src/transport/`, `thd75/src/aprs/`, `aprs/`, `aprs-is/`.

The code is defensively written, with a lot of explicit spec citations, extensive regression tests around historical bugs (byte-range guards, ambiguity, alt-encoding), and thoughtful choke points (CRLF-injection guard, bounded read line, spoofed-ack guard). The `unwrap`/`expect` uses in `aprs/src/build.rs` are all justified: they are `unwrap_or_else(|_| unreachable!(...))` on statically valid callsigns/tocalls or on invariants proved above the call. Real high-signal findings below.

## `aprs-is/` — TCP client to APRS-IS

- `aprs-is/src/client.rs:451` — Case-insensitive `logresp` matching not enforced. `line.contains("logresp")` / `line.contains("unverified")` / `line.contains("verified")` are all case-sensitive; a spec-compliant server that emits `LOGRESP` (some `javAPRSSrvr` builds and custom deployments use uppercase in the header) is silently treated as a comment line, so `LoggedIn` is never emitted and the client sits believing it is not yet authenticated. Also, `unverified` is detected via substring `contains` — a hostile server sending `# logresp N0CALL notverified, ...` (`verified` also substring-matches) is treated as verified.
- `aprs-is/src/client.rs:461` — When a receive-only client (`Passcode::ReceiveOnly`) sees `verified` in the response (i.e. the server actually granted RF gating despite the `-1` passcode), the code silently accepts it as `LoggedIn`. Not a bug per se, but a caller relying on `Passcode::ReceiveOnly` to guarantee "we won't gate to RF" should not trust the wire — the server can and will honor a real passcode carried in an out-of-band way.
- `aprs-is/src/filter.rs:170-224` — `AprsIsFilter::as_wire` performs no per-clause validation. Callsign / callsign-list fields (`Budlist`, `Prefix`, `Digi`, `Entry`, `Group`, `Unproto`, `Object`, `StrictObject`, `Friend`, `TypeAround`) are joined verbatim with `/`. An untrusted caller can inject `\n` / `\r` / space / `/` into a callsign to shift the wire form; the eventual `build_login_string` only rejects `\r\n` in the whole filter string. So `Filter::Budlist(vec!["N0CALL/1/2".to_owned()])` produces `b/N0CALL/1/2` — three names, not one. Minor because the filter is normally not attacker-controlled, but if any UI/library forwards user input into a `Vec<String>` filter clause the effect is undocumented.
- `aprs-is/src/client.rs:216-238` — Doc-string says the client is "not `Send`-across-the-await — typical usage is to own it from a single task"; the struct is in fact `Send` (composed of `Send` fields). The comment misdescribes it and should be removed or the constraint enforced.

## `aprs/` — parser, digipeater, messenger, `SmartBeaconing`

- `aprs/src/packet.rs:1029-1050` — `parse_aprs_third_party` extracts the raw inner payload but does not recurse. Callers who choose to `parse_aprs_data(payload)` can be recursively fed `}A>B:}A>B:}...` and blow the stack. Because there is no depth limit exposed for third-party frames, any downstream `IGate` code that re-parses payloads (like `format_for_is` chains) needs to know about this — worth a doc-comment warning if not an explicit depth counter.
- `aprs/src/packet.rs:494-511` — `parse_cse_spd` accepts `course == 0` and treats `000/000` as valid course/speed data, but APRS 1.0.1 §7 spec-wise defines `000` as "unknown". Downstream `AprsPosition.speed_knots = Some(0)` looks like a live "stationary" report rather than "no data". Compare to Mic-E's `decode_mice_speed_course` (mic_e.rs:236) which correctly maps course=0 → `None`. Data-fidelity nit, not a security bug.
- `aprs/src/packet.rs:1158` — `parse_aprs_user_defined` uses `*info.get(1)? as char` to extract the experiment ID. This treats byte 1 as an ISO-8859-1 codepoint, not as a UTF-8 character. Spec says one ASCII char; a byte 0x80..=0xFF becomes a Latin-1 char in the resulting struct rather than being rejected. Harmless if callers stringify it, misleading if they compare.
- `aprs/src/packet.rs:622-651` — `parse_dao` scans byte-by-byte for `!x_x!` patterns but does not require the two adjacent `!` bytes to be at UTF-8 char boundaries. Because the surrounding comment is a valid UTF-8 `&str`, this is safe in the current codepath, but it's a bare byte scan buried in a `&str` function — moving it to `&[u8]` (like the sibling `parse_cse_spd` header check) would be more honest about what it does.
- `aprs/src/mic_e.rs:120-137` — Mic-E longitude decode does `i16::from(d_byte) - 28`, `i16::from(m_byte) - 28`, `i16::from(h_byte) - 28`. Bytes are validated `>= 28` above (line 70) but not `<= 127`; the codepage byte range per spec is 28..=127. A byte `0xFF` (255) yields `d = 227`, then `d + lon_offset(0) = 227` — none of the `180..=189` / `190..=199` folds apply, so `lon_deg = 227`, `longitude_abs = 227 + …`, and we produce a longitude > 180°. No panic, but the caller gets a bogus decode instead of an `InvalidCoordinates`. The transmitter-side builder correctly clamps outputs to spec range; the receiver-side parser should reject bytes > 127.
- `aprs/src/mic_e.rs:131` — `if m >= 60 { m - 60 } else { m }` correctly folds the alt encoding, but `m` can legitimately be up to `127 - 28 = 99` given the byte-range gap above. If `m` is `120`, minutes = `60` — still ≥ 60 and unfolded. The single subtraction assumes the wire only ever puts m in `28..=88` (0..60) or `88..=119` (60..119, folded). Belt-and-suspenders: reject `m > 119` after fold.
- `aprs/src/message.rs:98`, `aprs/src/message.rs:100` — `MessageKind::Bulletin.number = b - b'0'` and `MessageKind::Announcement.letter = b as char`. The `b'A'..=b'Z'` guard is only applied to ASCII, so these are safe, but if the addressee is `BLN0` and the wire had a trailing lowercase in a group form, the classification differs subtly across releases (spec is uppercase-only). No bug found.
- `aprs/src/messenger.rs:150-163` — The message-ID allocation loop reserves the *whole* u16 space and skips already-pending IDs, but with `max_retries = 5`, the guard "far more than MAX_RETRIES of in-flight messages" is only true if the caller doesn't hold expired-but-uncleaned messages. Nothing here calls `cleanup_expired` before allocating, so an application that never polls `cleanup_expired` and keeps sending messages (each retained until `attempts >= max_retries`) can grow `pending_messages` unbounded — the loop then walks all of them per allocation (O(n²) total send cost) but does still terminate.
- `aprs/src/messenger.rs:145` — `send_message` never returns an error for messages the messenger cannot represent (e.g. > MAX_APRS_MESSAGE_TEXT_LEN). The doc-comment says "silently truncated"; the callee `build_aprs_message` does truncate. That's a real footgun for callers who need an authoritative wire ID — but the `_checked` sibling exists.
- `aprs/src/digipeater.rs:250-269` — Loop-detect uses `own_callsign_already_relayed`, which only trips on entries with `has_repeated == true`. It does NOT reject a packet whose *source callsign* is our own — an attacker (or a misconfigured station) transmitting `MYCALL>APK005,WIDE1-1:...` with our source is happily accepted, `has_repeated` never having been set by us, and we UI-frame-relay it. This is a well-known real APRS attack (source-spoof loops); a defense-in-depth check on `packet.source.callsign == self.callsign` would be cheap.
- `aprs/src/digipeater.rs:264-269` — Dedup key hashes source+destination+info but ignores the digipeater path. Two packets with different (unused) path tails but identical info are collapsed. This matches typical UIDIGI behavior, but a source-spoofing attacker can pin the same `(src,dst,info)` and every retransmission is deduped for the full TTL — no rate-limiting per source SSID.
- `aprs/src/digipeater.rs:395-404` — Case-insensitive callsign comparison but the SSID compare is strict `==`. A packet whose repeated hop matches our callsign but was digipeated with a different SSID (say we ran as `-9` but the digi in the path is our callsign at `-0`) is NOT loop-detected. In practice paths are marked with our exact address, but a heard-then-manipulated packet could bypass this.
- `aprs/src/station_list.rs:205-215` — `haversine_km` uses `2.0 * a.sqrt().asin()` — for exact antipodal points, floating-point rounding can push `a` slightly above 1.0, and `asin` returns `NaN`. Two APRS stations are extremely unlikely to be perfectly antipodal, but `nearby()`'s `NaN <= radius_km` is always false, so the antipodal peer silently disappears from the radius filter. Fix with `a.min(1.0).sqrt().asin()`.
- `aprs/src/smart_beaconing.rs:340` — `let interval = fraction.mul_add(-rate_range, f64::from(self.config.slow_rate_secs)) as u32;` — `rate_range` is `slow_rate_secs - fast_rate_secs` and assumed positive; if a caller configures `fast_rate_secs > slow_rate_secs`, the interpolation goes negative for high-speed input and the `as u32` cast saturates to 0, producing a beacon storm exactly at high speed. There is no ordering check between `slow_rate_secs` and `fast_rate_secs` in the config, so any test-fixture that swaps them accidentally will TX-storm.

## `aprs/src/build.rs` — 24 `unwrap`/`expect`

All checked. Every one is one of:
- `unwrap_or_else(|_| unreachable!("<statically valid>"))` on a compile-time-known callsign literal (e.g. `"APK005"`, `"N0CALL-7"`, `"WIDE1-1"`).
- `unwrap_or(default)` on a `.get()` slice that is proven in-bounds by an earlier bound check but re-checked to satisfy `-D clippy::indexing-slicing`.
- `str::from_utf8` on bytes constructed above from ASCII letters/digits (Mic-E destination), with an `unreachable!` guard that names the invariant.

The Mic-E cast suppressions at lines 996-1007, 1193-1316, 1343-1348 all cite spec table entries that bound the input. I verified the bounds match — they do. No unjustified `#[expect]` found.

## `thd75/src/transport/bluetooth.rs` and `bluetooth_mac.m`

- `bluetooth.rs:57-69` — `unsafe impl Send` and `unsafe impl Sync` for `BluetoothTransport`. `Sync` is claimed with the justification "concurrent read/write from multiple threads is safe" — but the trait methods take `&mut self`, so nothing in Rust ever exercises the `Sync` path. Removing `unsafe impl Sync` would harm nothing and reduce the unsafe surface.
- `bluetooth.rs:150` — `let handle_addr = self.handle as usize;` then `spawn_blocking` reifies it back to `*mut c_void`. The safety comment explains this survives `Drop` because "the C side serializes the entire write against close under its internal mutex". Verified in `bluetooth_mac.m:272` — `bt_rfcomm_write` holds `g_bt_mutex` while writing, and `bt_rfcomm_close:305` takes the same mutex to null the delegate pointer before freeing. However, the actual `free(ctx)` on line 317 is called *after releasing the mutex*, so if a Rust future is cancelled at exactly the wrong instant, Rust drops the `BluetoothTransport`, `Drop` (bluetooth.rs:272) calls `bt_rfcomm_close`, the ObjC side calls `free(ctx)`, then the still-pending `spawn_blocking` task acquires the mutex (now free), dereferences `ctx` via `ctx->channel` — use-after-free. The mutex protects contents but not the freed struct itself. Mitigating factor: this requires the exact interleaving; a `_Atomic int state` set to `-1` is checked first (bluetooth_mac.m:273 `ctx->state != 1`), but reading `ctx->state` on a freed pointer is the UAF. Fix: reference-count `RfcommContext` or move `free` under the mutex with a "no writes in flight" gate.
- `bluetooth.rs:302` — `pub use inner::BluetoothTransport;` is gated by `#[cfg(any(target_os = "macos", doc))]`. On any host that isn't macOS and isn't building docs, the entire module is empty; downstream code that references `BluetoothTransport` gets a "not found" error rather than a "not supported on this platform" error. Not a bug, but a stub with a `TransportError::PlatformUnsupported` would give better error messaging.
- `bluetooth_mac.m:99-107` — When the ingress pipe fills, the callback drops bytes and logs to stderr via `fprintf`. There is no rate limit on the log line, so a stuck consumer generates one log line per RFCOMM frame (worst case ~50 kB/s of stderr) that could itself block the main thread if stderr is line-buffered against a slow sink.
- `bluetooth_mac.m:210-211` — `for (int i = 0; i < 200 && ctx->state == 0; i++) CFRunLoopRunInMode(...)`. `ctx->state` is `_Atomic int` (line 63), but the wait loop still uses a busy 50 ms poll with a 10-second cap. If the peer takes >10s to open the channel (normal for a cold BT stack), open silently fails.
- `bluetooth_mac.m:41-46` — `bt_trace` uses `gmtime_r`, `[NSThread isMainThread]`, and a `fprintf`+`fflush` per call from inside `rfcommChannelData:`. When `THD75_BT_TRACE=1` is set, every inbound RFCOMM byte carries an unbuffered stderr write — that IS observable back-pressure on the main thread. Fine for a developer opt-in, but worth documenting that tracing itself perturbs the timing.
- `bluetooth.rs:23` — `fn bt_rfcomm_open(device_name: *const i8, ...)`. `i8` is macOS-correct for `c_char`, but the FFI would silently break under any hypothetical `c_char = u8` future. Using `std::ffi::c_char` would be portable and self-documenting.
- `bluetooth.rs:290` — Reimplementing `read(2)` via a private `extern "C"` block ("avoids libc dependency") duplicates a function that already exists in `libc`, which is already an implicit transitive dep. The custom binding does not respect the caller's expectations about `EINTR` — the read is called once and any `EINTR` bubbles up as an error via `io::Error::last_os_error()`, not retried. The tokio caller then treats it as a real read error. Minor.

## `thd75/src/aprs/client.rs`

- `client.rs:1213` — `let third_party_payload = format!("}}{header},{igate_call},I:{data}");` — `data` is caller-supplied (an APRS-IS line) and unsanitized before being placed in an AX.25 info field for RF transmission. Not itself dangerous (AX.25 does not split on CR/LF), but there is no upper length bound — a caller who forwards an oversized IS line will attempt to build an over-256-byte AX.25 info field. `build_ax25` may accept it, but many RF receivers truncate.
- `client.rs:1355-1361` — `should_gate_to_rf` — the guard `line.data.len() < 11 || line.data.as_bytes().get(10) != Some(&b':')` uses byte offsets on a UTF-8 `&str`. Because `from_utf8_lossy` replaces every invalid byte with U+FFFD (3 bytes), byte offsets after the first non-ASCII byte diverge from the intended message-format offsets: a message whose addressee field on the wire contained one invalid UTF-8 byte will have byte 10 land in the middle of a U+FFFD, the check will fail, and the packet will not be gated. That is safe (fail-closed) but silently drops legitimate traffic; documenting that the check is UTF-8-byte-based avoids surprise.
- `client.rs:1401-1406` — `auto_ack` sends an ack even for `MessageKind::AckRej` / `Bulletin` / `Announcement` / `GroupBulletin` / `NwsBulletin` if the addressee happens to equal `my_call`. Bulletins are normally addressed to `BLNx` etc., but nothing structurally prevents a spoofed one addressed to our callsign. Filtering `msg.kind() != MessageKind::Direct` before auto-ack would tighten this.
- `client.rs:1387` — `classify_ack_rej` runs on the message *text*, not on the addressee. A message with `text = "ack1"` from an addressee `MYCALL` will be classified as ack-rej regardless of whether it's really an ack. That's intended per spec, but note that a station that legitimately wants to send the literal text "ack1" cannot — the messenger will silently swallow it as a control frame. Minor UX / spec collision.

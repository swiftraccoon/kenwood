# Rust standards

This policy defines the Rust source, API and review requirements for the
workspace. New and changed code must satisfy applicable rules. Review changed
APIs, implementation and documentation through the contributor workflow.

The linked revisions fix the adopted text. Upstream changes require a policy
change that identifies affected rules, enforcement and existing code. The
executable baseline is Rust 1.94.0, including its Clippy and rustfmt components;
the nightly documentation URL does not change the workspace toolchain.

## Scope and precedence

The policy covers handwritten Rust libraries, binaries, build scripts, examples,
tests, benchmarks, standalone fuzz workspaces and developer automation. Public
APIs include traits, their implementer obligations, re-exports, feature-gated
items and Rust interfaces consumed through FFI. API rules also guide private
code, with abstractions limited to demonstrated needs.

Generated source follows its generator's policy. Change the generator and
regenerate affected outputs; preserve unrelated generated bytes. Rust API rules
apply to the handwritten FFI boundary. Native application sources retain their
language-specific requirements.

Apply requirements in this order:

1. Workspace and crate safety, protocol, ownership, dependency and lint rules in
   `AGENTS.md`, including the stronger documentation and panic restrictions.
2. The adopted Rust Style Guide and applicable Rust API Guidelines.
3. The enumerated Google additions.

Record a conflict explicitly. Readability is a criterion for choosing a compliant
design, not permission to remove validation or suppress a lint. Experimental
APIs may change to improve correctness and clarity; migrate workspace consumers
without compatibility shims.

## Source conventions

| Identifier | Requirement | Verification |
| --- | --- | --- |
| `S-FORMAT` | Follow the adopted Rust source layout, using the pinned formatter for mechanical layout. Record formatter limitations or overrides. | rustfmt checks in the local gate and CI, including each fuzz workspace. |
| `S-COMMENTS` | Apply the guide's comment placement, punctuation and line-width recommendations, with the workspace's contract-focused prose rules. | Review; formatter coverage is partial. |
| `S-MANIFEST` | Apply the guide's Cargo manifest formatting and metadata conventions. | Taplo, Cargo checks and review of conventions outside formatter coverage. |
| `S-NAMES` | Follow Rust naming, expression and module conventions. | Compiler and Clippy checks plus review. |

Formatter acceptance establishes mechanical layout only. Comment meaning,
manifest ordering and public naming require review.

The root `rustfmt.toml` fixes language and style editions at 2024, line width at
100, and field-initializer shorthand. The root Taplo configuration uses four
spaces for Cargo manifests and sorts ordinary table keys. Review package keys
in the guide's special order: `name`, `version`, remaining keys in version order,
then `description`. Author entries retain verified contributor identifiers;
invented names or contact details must not be added to match a preferred format.
This author-format deviation is reconsidered when publishing metadata changes.

## API applicability and adaptations

Review every entry of the adopted [checklist](https://github.com/rust-lang/api-guidelines/blob/19f0f62ecd0f56a0b7adaa332c352bc2476506ea/src/checklist.md).
Read the corresponding chapter before deciding applicability. A checklist title
is not a substitute for its qualifications and examples.

| Guideline | Workspace application |
| --- | --- |
| `C-PERMISSIVE` | Project deviation: existing manifest licenses apply. Standards adoption does not change licensing. Reconsider only with a separate project licensing decision. |
| `C-SERDE` | Project adaptation: add serialization for a demonstrated consumer need under the dependency policy. Use an optional feature where appropriate and preserve validated construction during deserialization. Reconsider when a serialization consumer is introduced. |
| `C-COMMON-TRAITS`, `C-CONV-TRAITS` | Implement semantically appropriate standard traits. Fallible conversions preserve validation; `Default`, ordering, copying and formatting must have meaningful contracts. |
| `C-COLLECT` | Bounded and validated collections retain rejection semantics. An infallible collection trait must not truncate, panic on ordinary input or bypass construction checks. Explain in the collection's API contract when a fallible operation is required. |
| `C-EXAMPLE` | Cover public functionality with useful executable examples or explicit links to shared examples. Avoid examples that only repeat obvious syntax. Hardware and network examples use `no_run` when execution requires an external service or device. |
| `C-FAILURE` | State error variants and triggers, panic conditions where applicable, and unsafe caller obligations. Async and I/O contracts also state cancellation, partial progress, deadlines, completion boundaries and cleanup behavior. |
| `C-VALIDATE` | Scoped deviation: retain the documented unknown-to-idle behavior of `mmdvm-core::ModemMode::from_byte` and its status parsers. Reconsider if the fallback policy changes or another modem mode becomes supported. |
| `C-NO-OUT` | Return produced values directly. Caller-owned buffer reuse follows the exception already described in the upstream guideline. |
| `C-OBJECT`, `C-SEALED` | Decide trait-object support and downstream implementation deliberately. Transport and extension traits retain the implementation capabilities their contracts require. |
| `C-STRUCT-PRIVATE`, `C-NEWTYPE-HIDE` | Protect invariants through encapsulation. Independently validated passive records may expose fields when every field combination remains valid. |
| `C-BITFLAG` | Represent independently combinable flags as a validated bitset; represent mutually exclusive choices as enums. Evaluate a supporting crate under the dependency policy. |
| `C-METADATA`, `C-RELNOTES`, `C-STABLE` | Apply publishing and release requirements to the relevant crate and release state. Optional homepage and documentation fields remain optional. Experimental API changes still describe consumer impact. |

All other entries apply as written, subject to the precedence above. Assess
applicability from the API mechanisms and intended use. Implement a trait only
when its semantics support the crate's contract.

## Selected Google additions

The governing principle is:

> Style rules should prioritize readability and maintainability over writeability.

The following identifiers select additional review requirements from the
[adopted Google guide](https://github.com/google/styleguide/blob/3cf4f72013826804b7442896ce84d3777cf89ae0/rustguide.md).

| Identifier | Requirement |
| --- | --- |
| `G-READABILITY` | Prefer code whose behavior and invariants are clear to readers. |
| `G-TYPES` | Add explicit types where inference obscures meaning. |
| `G-ITERATION` | Use direct loops when iterator chains obscure control flow; retain clear, concise combinators. |
| `G-FIELDS` | Use named fields for ambiguous positional data. |
| `G-ABSTRACTION` | Prefer standard facilities; give traits and macros a concrete purpose. |
| `G-OWNERSHIP` | Prefer borrowing and unique ownership where practical; justify cloning and shared ownership by their use. |
| `G-FORMAT-SKIP` | Limit formatting exclusions to justified alignment or generated content. |
| `G-HIDDEN-API` | Avoid dependencies on another crate's hidden implementation APIs. |

Google's platform-specific organization, build, threading, async and test
framework prescriptions are excluded. Non-exhaustive types, poisoned-lock
recovery and panic containment require individual contract review. The existing
workspace documentation and panic rules remain in force.

## Enforcement and review

Use the [contributor workflow](CONTRIBUTING.md) for every change. Preserve the
denied lint groups and run the complete local gate on the finished working tree
before committing. Reuse its result while only commit boundaries change; check
new intermediate API combinations according to the contributor workflow. Validate
relevant platform and isolated feature configurations, and run cross-platform
local CI before pushing.

Automation checks syntax, selected contracts and exercised behavior. Review
establishes applicability, useful examples, API discoverability, trait semantics
and readability. Document checks as automated, manual or mixed; do not describe
a manual requirement as fully enforced by Clippy.

Review changed code against applicable `S-*`, `C-*` and selected `G-*` rules.
Resolve concrete findings with the change. Keep API-specific contracts and
limitations in rustdoc and READMEs. Record enduring policy adaptations here,
with their exact scope, rationale and reconsideration condition; update them
when affected APIs, features, dependencies or adopted rules change.
